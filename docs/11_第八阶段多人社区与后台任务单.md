## 1. 主对话职责与交付范围

主对话统筹需求、契约、依赖、评审、集成和验收；不将某一侧自测结论当作全项目完成。A/B 分工沿用页面与数据优势，但后台也是正式交付，不作为任何一侧的附带任务。

整体交付是小程序 + 云服务 + 管理后台；先实现一个真实闭环，再覆盖完整功能。每周精选、官方评论属于必交范围。

## 4. 并行与串行安排

1. 主对话先统一接口/路由/状态（E8-02），负责人提供环境条件（E8-01）。
2. A 搭后台与日记页面；B 实现身份、课程和日记服务，可并行。公共文件由任务指定的一位实际编辑者提交，另一侧审查。
3. 集成“后台发布课程 → 小程序体验”和“甲私密日记 → 发布 → 乙看到”两个最小闭环，先解决数据与权限问题。
4. A 完成社区和官方后台界面；B 实现互动、官方写入与治理服务，可并行。
5. 合并与最终端到端验收串行执行，以同一候选提交为准。

分支可继续使用 `feat/experience-ui`、`feat/assessment-data`；开工先同步 main。文档更新和统一集成由主对话负责。不自动向其他任务发送指令，任务单可以直接交给合作开发者。

## 5. 首个可运行增量

最先交付：云端身份 → 一门后台发布的多肉课程 → 完整旧体验 → 新建日记 → 私密保存 → 发布审核 → 第二账号看到 → 撤回不可见。

该增量验证基础架构，不代表阶段完成。点赞、评论、官方运营与后台治理全部通过后才允许冻结本阶段。

## 7. 检查与交接

现有检查保留：`check:mock`、`check:assessment`、`check:experience`、`check:completeness`、`check:demo`、小程序构建。依赖变化时运行安装与 peers 检查。

实施中新增有意义的云服务契约/权限/并发测试、后台构建与云端部署验证。不要只检查源码含某个字符串来证明授权正确。将 `check:completeness` 的社区禁令改为状态/权限/无私聊断言，将 `check:demo` 路由基线更新为 17 页和原 5 Tab；允许配置的云资源而非任意外部 URL。不得整段删除测试以获得绿灯。

每次交接提供：任务 ID、基线/提交、实际修改范围、接口变更、自动验证结果、真实运行与未验证项、复现步骤、环境依赖。敏感成员数据和完整 OpenID 不进 Git。

主对话维护集成顺序和冲突处理，验收必须区分测试替身与真正云服务，不接受“页面已完成”替代数据/权限验收。
